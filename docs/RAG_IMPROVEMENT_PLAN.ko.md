# 기억 회수(RAG) 개선안

[RAG_ANALYSIS.ko.md](RAG_ANALYSIS.ko.md)의 실측을 근거로 한 단계별 개선안이다.
각 단계는 **독립적으로 배포하고 되돌릴 수 있게** 쪼갰다. 운영 중인 Masamo를
멈추지 않는 것이 전제다.

## 목표

"자연스럽다"는 두 가지가 동시에 맞아야 한다.

- **회수율** — 물어보면 찾아온다. 지금 이상적 회수 대비 0.04였고 1단계 후 0.35다.
- **정밀도** — 관련 없으면 조용히 있는다. 지금 잡담 8건 중 **8건 전부** 기억이
  주입된다.

병목은 셋이다.

1. ~~후보 정렬이 공용 대화 기억을 밀어냄~~ → 1단계에서 해결
2. **임계값이 아무것도 거르지 않음** — 잡담에도 6~14개 기억이 들어감 → 2단계
3. **후보를 시간으로 자름** — 질의 벡터가 DB에 전달되지 않아 최신 384건만 대상 → 3단계

회수율만 올리면(3단계만 하면) 정밀도가 더 나빠져 체감은 오히려 떨어진다.
**2단계를 먼저 해야 하는 이유다.**

## 1단계 — 스코프 우선 정렬 제거 · 완료

`fetch_recent_memory_entries`의 `ORDER BY CASE ...`를 제거했다. 실제 코드가
생성하는 SQL을 운영 DB에 그대로 돌려 검증했다.

| 사용자 | 본인 기억 | 전: 공용 | 후: 공용 |
|---|---:|---:|---:|
| kfc408 | 2,965 | **0** | 221 |
| cream | 1,504 | **0** | 313 |
| 박진석 | 1,397 | **0** | 232 |

회귀 방지: `tests/memory_scope_window_spec.py`.

### 이 단계가 만든 부작용 하나

윈도가 384개로 고정된 채 공용 기억이 자리를 나눠 가지므로 **시간 깊이는 오히려
얕아졌다.**

| 사용자 | 전: 가장 오래된 후보 | 후: 가장 오래된 후보 |
|---|---|---|
| cream | 2026-06-07 | 2026-07-20 |
| kfc408 | 2026-07-09 | 2026-07-22 |

품질은 9배 좋아졌지만(0.04 → 0.35) 이건 **자리 재분배**일 뿐 근본 해결이
아니다. 2단계가 필요한 이유다.

## 2단계 — 정밀도 · 완료

**이 단계를 건너뛰고 3단계를 하면 체감이 오히려 나빠진다.** 실측으로 확인했다.

### 문제: 임계값 0.5가 아무것도 거르지 않는다

장기기억이 전혀 필요 없는 발화 8개("ㅇㅇ", "안녕", "고마워", "지금 몇 시야" …)를
넣고, 임계값을 넘어 프롬프트에 주입되는 기억 수를 셌다.

| 조건 | 후보 풀 | 잡담에 주입되는 기억 | 기억 필요 질문 최고점 | 잡담 최고점 |
|---|---:|---:|---:|---:|
| 현재 | 384 | 6.6개 | 0.621 | 0.531 |
| 1단계 적용 후 | 384 | 11.9개 | 0.657 | 0.546 |
| 벡터 검색 적용 시 | 7,140 | **14개 (상한 포화)** | 0.678 | 0.570 |

**잡담 8건 중 8건 전부** 기억이 주입된다. 넓힐수록 심해진다.

```
"ㅇㅇ"        → 0.534  기상청 API 좌표값 대화
"안녕"        → 0.554  안랩 채용 겹치는지 대화
"고마워"      → 0.567  관계없는 잡담
"지금 몇 시야" → 0.568  치킨 몇 시에 시키냐는 대화
```

원인은 **E5 코사인이 절대 척도가 아니라는 것**이다. 관련 없는 한국어 문장끼리도
0.5~0.6이 나온다. 기억이 필요한 질문의 최고점 평균이 0.678, 잡담이 0.570 —
**차이가 0.108뿐이다.** 0.5는 사실상 "전부 통과"다.

그런데 코드는 임계값이 걸러줄 것이라 **명시적으로 가정**하고 있다.

- `_should_search_memory` docstring: *"실제 관련성은 검색 임계값이 다시 검증하므로
  무관한 기억을 프롬프트에 강제로 넣지는 않습니다"*
- `ai_handler`에서 전역 0.60 게이트를 일부러 제거한 주석 (구조화 메모리 0.50을
  존중하기 위해)

이 가정이 실측으로 틀렸다. 도구를 쓰지 않는 모든 대화에 최대
`RAG_HYBRID_TOP_K = 8`개 블록이 들어간다.

### 할 것

**2-a. 순수 의미 점수 절대 관문 + 상대 기준.** 어휘·개인 가산점은 순위에만
쓰고 관문은 `semantic_similarity`로만 판단한다. 관문을 넘은 후보 중에서도
최고 종합점수 대비 일정 비율 안에 드는 것만 남긴다.

**2-b. 의도별 관문.** 평범한 대화의 얕은 검색은 `0.61`, “전에 뭐라고 했지”처럼
명시적으로 기억을 요구한 깊은 검색은 recall을 위해 `0.58`을 쓴다.

**2-c. 주입 개수 축소.** `RAG_HYBRID_TOP_K`를 8에서 2~3으로 줄인다. 사람이
대화할 때 과거 기억 8개를 동시에 떠올리지 않는다.

**2-d. 리랭커 검토.** `RERANK_ENABLED=False`다. cross-encoder는 절대 척도가
훨씬 나아서 이 문제에 정확히 맞다. 다만 CPU 1스레드에서 지연이 붙으므로
2-a~2-c로 충분한지 먼저 본다.

**2-e. 점수 오염 정리.** 현재 `similarity`는 순수 코사인이 아니라
`코사인 + 어휘보너스(최대 0.08) + 본인범위보너스(0.025)`다. 임계값을 조정하려면
무엇을 기준으로 자르는지부터 분명해야 한다.

### 적용 결과 (운영 기억 실측)

순수 의미 점수에 `RAG_MEMORY_GATE_SCORE=0.61`(명시적 기억 질문 `0.58`),
`RAG_MEMORY_RELATIVE_FLOOR=0.94`, `RAG_MEMORY_MAX_BLOCKS=3`을 적용하고 같은
데이터로 다시 쟀다. 어휘 일치와 본인 범위 `+0.025`는 최종 후보의 순위만
바꾸며 관문을 우회하지 못한다.

| 조건 | 잡담 16건에 주입 | 기억 질문 12건 회수 | 평균 주입 블록 |
|---|---:|---:|---:|
| 적용 전 | 16/16건 (6.6~14개) | 12/12 | 6.6~14 |
| **적용 후 (384행)** | **0/16건** | 11/12 | 3.25 |
| **적용 후 (전수)** | **0/16건** | 11/12 | 2.67 |

잡담에 기억이 하나도 들어가지 않으면서, 기억이 필요한 질문 12건 중 11건은
그대로 회수된다. 못 찾은 1건은 최고 유사도가 0.605로 게이트 바로 아래였다.

`RAG_MEMORY_MAX_BLOCKS`는 embedding config 파일이 아니라 코드/env에서 읽는다.
이미 배포된 서버의 `emb_config.json`(현재 `hybrid_top_k: 8`)을 고치지 않아도
새 상한이 적용된다.

회귀 방지: `tests/rag_relevance_gate_spec.py`.

## 3단계 — 서버측 벡터 검색 · Masamo 적용 완료

### 무엇을 바꾸나

지금은 "최신 384건을 받아와 파이썬에서 코사인 계산"이다. 이걸 "DB가 전체에서
가장 비슷한 32건을 골라서 준다"로 바꾼다. 최종 프롬프트에는 관문과 상대
기준을 통과한 최대 3개만 들어간다.

```sql
-- 지금
... WHERE <스코프 조건> ORDER BY timestamp DESC LIMIT 384

-- 바꾼 뒤
... WHERE <스코프 조건> ORDER BY VEC_COSINE_DISTANCE(embedding_vec, ?) LIMIT 32
```

### 벡터 인덱스는 만들지 않는다 (만들 수 없다)

TiDB의 HNSW 벡터 인덱스는 TiFlash 레플리카를 요구하는데, 이 클러스터에는
TiFlash가 없다(`information_schema.TIFLASH_REPLICA`가 비어 있음). 이미 `vector(384)`를
쓰는 `kakao_chunks`도 인덱스 없이 동작한다.

**인덱스 없이도 충분하다.** 실측:

| 대상 | 행 수 | 전수 벡터 정렬 |
|---|---:|---:|
| `kakao_chunks` (측정) | 13,282 | **0.403초** |
| 한 사용자의 스코프 대상 (추정) | ~7,140 | ~0.2초 |

7,140행은 cream 기준 `채널 공용 5,636 + 본인 1,504`다. 추정치는 kakao 측정에서
선형 외삽한 값이므로, 3-c 단계에서 실제로 재야 한다.

### 비용 — 무료 플랜 기준으로 계산

TiDB Cloud Starter 무료 플랜(월 50M RU, row 5 GiB)을 계속 쓴다는 전제로 실제
트래픽을 재서 계산했다.

**측정한 현재 상태**

| 항목 | 실측값 |
|---|---:|
| DB 전체 크기 | **27.9 MB** (5 GiB의 0.5%) |
| AI 대화 턴 | **49건 / 7일 = 하루 약 7건** |
| 검색 1회 전송량 | 1,183 KiB |

**바꾼 뒤 (추정)**

| 항목 | 지금 | 바꾼 뒤 | 방향 |
|---|---:|---:|---|
| 봇으로 내려오는 데이터 | 1,183 KiB/검색 | ~43 KiB/검색 | 27배 감소 ✅ |
| DB가 읽는 데이터 | ~1.2 MB/검색 | ~11 MB/검색 | 약 9배 증가 ⚠️ |
| 저장 공간 | 27.9 MB | ~63 MB | 5 GiB의 1.2% ✅ |
| 회수 품질 | 0.35 | **1.00** | ✅ |

**월 RU 환산.** 읽기 RU를 64 KiB당 1 RU로 잡고 하루 7회 검색 기준:

| | 검색당 | 월간 | 무료 한도 대비 |
|---|---:|---:|---:|
| 지금 | ~19 RU | 약 4천 RU | 0.008% |
| 바꾼 뒤 | ~172 RU | 약 3.6만 RU | **0.07%** |

**즉 9배가 늘어도 월 한도의 0.1% 미만이다.** 제 RU 모델이 100배 틀려도 7%다.
하루 검색이 70회로 10배 늘어도 0.7%다.

앞서 "품질과 비용이 같이 좋아진다"고 했다가 "RU가 늘어날 수 있다"고 정정했는데,
실제 트래픽으로 계산하니 **둘 다 실질적으로 틀린 걱정이었다.** 이 규모에서
RU는 제약이 아니다. 진짜 제약은 저사양 서버의 CPU인데, 벡터 거리 계산이 봇이
아니라 **DB 쪽으로 넘어가므로 오히려 유리하다.**

다만 추정은 추정이므로, 켠 뒤 TiDB Cloud의 **Usage this month** 패널로 3일간
확인한다. SQL 쪽 RU 통계(`mysql.request_unit_by_group`)는 값이 최신이 아니라
신뢰하지 않는다 — 확인해보니 2026-05-20자 한 행만 남아 있었다.

만약의 경우를 대비해 `WHERE`에 기간 상한(예: 최근 180일)을 넣는 선택지는 남겨
두지만, 위 계산상 필요하지 않을 것이다.

### 작업 순서

**3-a. 열 추가 (비파괴)**

```sql
ALTER TABLE discord_memory_entries ADD COLUMN embedding_vec VECTOR(384) NULL;
```

기존 `embedding BLOB NOT NULL`은 **그대로 둔다.** 롤백이 곧 플래그를 끄는
것이 되도록.

**3-b. 백필**

기존 BLOB을 읽어 `[f1,f2,...]` 텍스트로 바꿔 새 열에 넣는다. 새로 임베딩을
계산하지 않으므로 결과는 동일하다. 전용
`scripts/apply_memory_vector_column.py`는 작은 배치와 휴식 간격을 쓰며,
배치 수·실행 시간·진행량 상한이 있어 불량 행에서 무한 반복하지 않는다.
기존 BLOB은 읽기만 하고, 행 수와 원본 바이트가 감소하면 실패한다.

```bash
MASAMONG_ENV_FILE=/etc/masamong/masamo.env \
  .venv/bin/python scripts/apply_memory_vector_column.py \
  --expected-profile masamo --expected-db masamong --apply \
  --confirm "ADD COPY VECTOR COLUMN TO masamong"
```

**3-c. 커버리지 확인**

```sql
SELECT COUNT(*) AS total,
       SUM(CASE WHEN embedding_vec IS NULL THEN 1 ELSE 0 END) AS missing
FROM discord_memory_entries;
```

`missing = 0`이 아니면 다음으로 넘어가지 않는다. 이때 3-b 이후의 실제 스캔
시간도 함께 잰다.

**3-d. 쓰기 경로**

`upsert_memory_entry`가 두 열을 **함께** 쓴다. 이래야 플래그를 껐다 켜도
데이터가 어긋나지 않는다.

**3-e. 읽기 경로 + 기능 플래그**

```dotenv
STRUCTURED_MEMORY_VECTOR_SEARCH_ENABLED=false   # 새 인스턴스 기본값
STRUCTURED_MEMORY_VECTOR_TOP_K=32
```

`fetch_recent_memory_entries`에 벡터 경로를 추가하되, 다음 중 하나라도 아니면
자동으로 기존 경로로 내려간다.

- 플래그가 꺼져 있음
- `embedding_vec` 열이 없음
- 기존 BLOB 중 `NULL` 벡터가 하나라도 남아 있음
- 벡터 SQL이 한 번이라도 실패함

Masamo는 전체 커버리지를 확인한 뒤에만 켠다. General은 현재 운영 서비스가
없으므로 별도 DB와 서비스가 준비되기 전에는 이 마이그레이션 대상이 아니다.

**3-f. 본인 기억 우대 유지**

`_score_discord_rows`의 `+0.025` 가산은 그대로 둔다. 최종 3개보다 넉넉한
32개를 받아 파이썬에서 어휘·본인 가산 후 다시 정렬한다.

### 검증

- 오프라인: 벡터 경로와 기존 경로가 **같은 코퍼스**에서 같은 상위 결과를 내는지
- 운영: 2-c의 커버리지 + Usage 패널 RU 관찰 최소 3일
- 롤백: 플래그만 끄면 즉시 원복. 열과 데이터는 남는다

### 2026-07-29 Masamo 운영 적용 결과

- 기능 검증 SHA: `b1cb1ca4a69b447ac1c8aab9972259671c11d160`
- 기존 BLOB: **23,100행 / 35,481,600바이트**, 차원 불일치 0
- 새 `embedding_vec`: 미백필 0, 런타임 신규 기억도 BLOB·VECTOR 동시 기록
- 운영 설정: `STRUCTURED_MEMORY_VECTOR_SEARCH_ENABLED=true`,
  `STRUCTURED_MEMORY_VECTOR_TOP_K=32`
- 강제 read-only 헬스체크: 메인 DB, 384차원 임베딩, Discord 저장소,

- TiDB 논리 사용량: 약 **29.55MB / 5GiB (0.55%)**

월 RU는 SQL에서 최신 값을 제공하지 않아 TiDB Cloud의 **Usage this month**가
최종 기준이다. 현재 하루 약 7회 검색을 기준으로 한 추정은 월 3.6만 RU,
무료 50M RU의 약 0.07%다. 새 경로는 LLM 호출을 추가하지 않는다.

## 4단계 — 죽은 fallback 정리 (청소)

`discord_chat_embeddings`는 봇 런타임이 쓰지 않는다(`upsert_message_embedding`
호출부가 스크립트뿐). 마지막 기록이 **2026-04-02**이고, `conversation_history`는
2026-04-29부터라 시간 범위가 겹치지 않아 조인 결과가 0건이다.

그런데 `_embedding_candidates`는 구조화 후보가 비었을 때 이 테이블을 fallback으로
읽는다. **4개월 전에 멈춘 데이터를 비상 경로로 쓰고 있다.**

3단계 후에는 구조화 후보가 비는 일이 사실상 없어지므로, **fallback 경로를
제거**하는 쪽을 권한다. 테이블은 지우지 말고 남겨둔다(2,913행, 0.4MB).

되살리는 선택지도 있지만, 원문 단위 임베딩은 구조화 기억과 내용이 겹치고
저사양 서버에서 재색인 비용이 든다. 3단계 결과를 보고 판단해도 늦지 않다.

---

## 5단계 — 기억 단위 품질

2단계로 회수는 해결되지만, **회수해온 것의 질**은 따로 문제다.

**5-a. 본문 중복.** `compose_memory_text`가 `f"{summary}\n{context}"`를 반환하는데,
본인 범위 단위는 요약과 원문이 같은 문장이라 **같은 문장이 두 번** 들어간다.
신규 `guild_user` 33건 전부가 이 형태다(운영 확인). 아직 33건이라 지금이 싸다.
요약과 원문이 같으면 하나만 넣도록 고친다.

**5-b. 키워드 추출.** 운영 실제 값: `["그렇네","이미지","생성","한세월이었는데","어캐바꿈","뭔가"]`.
`extract_keywords`가 앞에서부터 2글자 이상 토큰을 담을 뿐이라 "그렇네", "뭔가"가
핵심 키워드가 된다. 지금은 벡터 본문에 들어가지 않아 회수에 직접 영향은 없지만,
표시용·필터용으로 쓸 수 없는 상태다. 한국어 불용어 목록을 늘리거나, 이 필드를
쓰지 않기로 정하고 저장을 멈춘다.

**5-c. 기억 폭증.** 메시지 하나가 `user` + `channel` 두 행을 만들어 20,549개
메시지에서 23,075개 기억이 나왔다. 3단계 후에는 전수 검색이라 양 자체는 문제가
아니지만, 단발 발화("ㅇㅇ", "그렇네")까지 독립 기억이 되는 건 노이즈다.
`is_meaningful_text` 기준을 올리는 것을 검토한다.

## 6단계 — 대화 창 복구와 어휘 검색

`config.py`에 `BM25_ENABLED = False`, `BM25_DATABASE_PATH = None`이 하드코딩돼
있어 `bm25_manager`가 `None`이다. 그 결과 두 가지가 죽어 있다.

**6-a. 대화 창 확장이 같이 죽었다 (더 중요).** `_resolve_dialogue_messages`는
주변 대화를 이렇게 가져온다.

```python
if message_id is not None and self.bm25_manager is not None:
    window = await self.bm25_manager.fetch_window_for_message(...)
    ...  neighbors = await self.bm25_manager.fetch_neighbors(radius=self.neighbor_radius)
```

`bm25_manager`가 `None`이라 이 블록 전체가 건너뛰어진다. `CONVERSATION_NEIGHBOR_RADIUS = 3`은
**죽은 설정**이다. 회수한 기억은 저장 시점에 굳은 `raw_context`만 달고 온다.

다만 실측상 영향은 스코프에 따라 다르다.

| scope | 행 수 | `raw_context` 평균 길이 | 내용 |
|---|---:|---:|---|
| `channel` (공용) | 7,292 | 196자 | 여러 화자의 실제 대화 |
| `user` (본인) | 15,734 | 77자 | 그 사람 한 줄뿐 |

**1단계 이전에는 공용 기억이 아예 회수되지 않았으므로, 회수된 기억 100%가
문맥 없는 한 줄이었다.** 1단계로 공용 기억이 들어오면서 이 문제는 상당 부분
저절로 완화됐다. 남은 개선은 저장 시점 스냅샷 대신 **조회 시점에
`conversation_history`에서 주변 발화를 읽는 것**이고, 여기에 BM25는 필요 없다.

**6-b. 어휘 검색.** `_bm25_candidates`는 항상 빈 목록을 반환하므로
**"하이브리드 검색"은 실제로 밀집 검색 단독**이다.

고유명사·오타·정확한 어휘가 중요한 질문("그 게임 이름 뭐였지")은 임베딩만으로는
약하다. 다만 별도 인덱스를 유지하는 비용이 있다.

**2·3단계를 먼저 하고, 그래도 남는 실패 사례를 모은 뒤에 판단할 것을 권한다.**
지금 켜면 무엇이 개선된 건지 구분하기 어렵다.

BM25 대신 TiDB의 전문 검색이나 `keyword_json` 기반 필터를 쓰는 방법도 있는데,
5-b를 먼저 고쳐야 의미가 있다.

## 하지 말아야 할 것

측정해보고 **버린** 안이다.

**스코프 할당(공용 50% / 본인 50%).** recall@5 = 0.21로, 그냥 최신순(0.35)보다
나빴다. 공용 기억이 본인 기억보다 정보 밀도가 높은데(평균 439자 대 212자) 인위적
비율로 자르면 최근 맥락을 놓친다.

**LIMIT만 올리기.** 2,000으로 올려도 11% 커버에 그치고 전송량만 5배가 된다.
`TIDB_STARTER_FREE_PLAN_MODE`가 384로 다시 조이는 것도 이유가 있다.

**임베딩 모델 교체.** 데이터는 건강하다 — 384차원 전량 정상, 결측 0, 중복 0.2%.
지금 실패는 모델이 후보를 못 고른 게 아니라 **후보에 정답이 없었던** 것이다.
모델을 바꿔도 3단계 전에는 나아지지 않는다.

## 요약

| 단계 | 내용 | 고치는 것 | 위험 | 상태 |
|---|---|---|---|---|
| 1 | 스코프 정렬 제거 | 회수율 0.04 → **0.35** | 없음 | **완료** |
| 2 | 정밀도 (게이트·상한) | 잡담 주입 6.6개 → **0개** | 낮음 | **완료** |
| 3 | 서버측 벡터 검색 | 회수율 0.35 → **1.00** | 운영 DDL | **Masamo 적용·검증 완료** |
| 4 | 죽은 fallback 제거 | 없음 (청소) | 낮음 | 아무 때나 |
| 5 | 기억 단위 품질 | 간접 (지금 33행) | 낮음 | 아무 때나 |
| 6 | 대화 창 복구 · 어휘 검색 | 회수한 기억의 문맥 | 중간 | 3단계 후 |

**순서가 중요하다.** 2단계 없이 3단계를 하면 회수 범위가 384행에서 7,140행으로
넓어지면서 잡담에 주입되는 기억이 6.6개에서 14개로 늘어난다. 체감은 더 나빠진다.

4·5단계는 개선이 아니라 청소다. 실질적인 개선은 **1·2·3단계**다.

운영 DDL이 필요한 건 3단계뿐이다. 나머지는 코드·설정 변경이고 되돌리기 쉽다.
